# Tusk Rebuild Specification

> Canonical product and system specification for rebuilding Tusk from zero.

| Field | Value |
|---|---|
| Status | Approved rebuild baseline |
| Spec ID | `TUSK-SPEC-000` |
| Version | `0.2.0` |
| Language policy | Indonesian context, English normative contracts |
| Target host | Termux on Android, with architecture detected at runtime |
| Container engine | Podman inside the Smart Engine's selected execution backend |
| License intent | Open source; final repository license must be selected before release |

## 1. Authority and Reading Rules

### 1.1 Status dokumen

Dokumen ini adalah source of truth untuk pembangunan ulang Tusk. Dokumen lama,
kode lama, README lama, handoff lama, dan perilaku prototipe lama hanya boleh
digunakan sebagai bahan sejarah. Jika ada konflik, dokumen ini yang menang.

The following keywords are normative:

- **MUST** and **MUST NOT** define release-blocking requirements.
- **SHOULD** and **SHOULD NOT** define strong defaults that require a documented
  reason to violate.
- **MAY** defines optional behavior.
- A feature is not "supported" until its acceptance criteria pass.
- Placeholder output, simulated success, and fake state MUST NOT satisfy a
  requirement.

Every normative requirement has a stable identifier. Implementations, tests,
release notes, and follow-up specifications MUST reference these identifiers.

### 1.2 Product definition in one sentence

**Tusk makes real Podman workflows usable in unprivileged Termux by testing and
selecting the most suitable execution backend for the current device.**

### 1.3 Definisi penting

| Term | Meaning |
|---|---|
| Host | Android/Termux environment where the user invokes Tusk and Podman commands |
| Container engine | Real Podman instance that owns images, containers, networks, volumes, and builds |
| Smart Engine | Tusk subsystem that discovers, tests, benchmarks, ranks, and selects execution backends |
| Backend | A concrete environment capable of hosting Podman, such as proot or a QEMU system VM |
| Backend instance | Initialized backend plus its isolated persistent Podman data |
| Guest | Linux environment supplied by a backend; it may be a VM guest or a proot rootfs |
| Podman shim | Host command named `podman` that forwards commands to the selected backend |
| Shared root | Explicit host directory exported to the guest for build contexts and bind mounts |
| Qualified | Backend passed the mandatory real Podman conformance suite on this device |
| Ready | Selected backend is running, Podman is healthy, and required integration is available |

## 2. Spirit and Product Intent

### 2.1 Masalah yang diselesaikan

Container engine Linux tidak dapat diasumsikan berjalan secara normal langsung
di Termux tanpa root karena
Android tidak memberikan kombinasi kernel feature, namespace, cgroup, mount,
overlay filesystem, dan daemon environment yang biasanya dibutuhkan. Mencoba
membangun container runtime palsu di host hanya memindahkan masalah dan
menghasilkan kompatibilitas yang rapuh.

Tidak boleh ada asumsi tunggal bahwa satu pendekatan selalu paling baik. Pada
sebagian perangkat, proot mungkin lebih ringan; pada perangkat atau workload
lain, QEMU system ARM64, x86_64, atau arsitektur lain mungkin lebih kompatibel.
Tusk harus mencoba kandidat yang tersedia, membuktikan bahwa Podman benar-benar
berfungsi, mengukur hasilnya, lalu memilih backend terbaik secara transparan.

### 2.2 Spirit

> Hardware emulation for Termux, because sometimes working is better than fast.

The product values are:

1. **Real behavior over simulated success.** A slow real container is better
   than a fast placeholder.
2. **Reuse the ecosystem.** Podman owns container semantics; proot/QEMU own
   execution boundaries; Tusk owns discovery, selection, and integration.
3. **Podman at the boundary.** Users invoke real Podman commands from Termux;
   Tusk does not pretend that Podman is Docker.
4. **Evidence before preference.** A backend becomes preferred only after real
   conformance tests and repeatable benchmarks on the current device.
5. **Safe, recoverable state.** Installation, backend lifecycle, updates, and selection
   switching must survive interruption.
6. **Mobile constraints are first-class.** No root, no KVM assumption, limited
   RAM, Android process killing, and Termux paths are design inputs.

### 2.3 Product requirements

- `PROD-001`: Tusk MUST run without Android root access.
- `PROD-002`: Tusk MUST NOT require `/dev/kvm`; acceleration MAY improve a QEMU
  candidate but MUST NOT be assumed.
- `PROD-003`: Container operations MUST be performed by real Podman in the
  selected backend.
- `PROD-004`: Tusk MUST NOT implement a parallel OCI image store, container
  runtime, build engine, network manager, volume manager, or Compose engine.
- `PROD-005`: A successful command MUST represent a completed real operation.
- `PROD-006`: Unsupported behavior MUST fail with a non-zero exit code and an
  actionable message; it MUST NOT be ignored silently.
- `PROD-007`: Tusk MUST preserve Podman exit codes for forwarded commands.
- `PROD-008`: The initial production target MUST include ARM64 Android, while
  host and backend architecture MUST be detected rather than hardcoded.
- `PROD-009`: Normal installation and use MUST NOT require building Tusk or a
  guest image from source.
- `PROD-010`: The MVP MUST provide a Smart Engine that evaluates all packaged
  backend candidates applicable to the current device before recommending one.

## 3. Goals, Non-Goals, and Success

### 3.1 Goals

- Install a functional Podman execution backend non-interactively.
- Use `podman` and `podman compose` syntax from Termux.
- Pull, build, run, inspect, stop, remove, and log real containers.
- Persist images, containers, networks, and volumes across VM restarts.
- Make published TCP ports reachable from Termux.
- Support explicit host directory sharing and bind mounts.
- Probe proot and supported QEMU architecture candidates instead of assuming a
  universal best backend.
- Rank qualified candidates using correctness, reliability, speed, memory, and
  storage measurements.
- Recover from stale sockets, interrupted downloads, and unclean VM exits.
- Expose enough diagnostics that failures can be understood without reading
  source code.

### 3.2 Non-goals for MVP

- Running Docker Engine or `dockerd` in any backend.
- Making Docker CLI compatibility the primary product interface.
- Kubernetes or multi-node orchestration.
- Silently distributing one logical Podman store across multiple backends.
- Per-container VMs.
- Windows containers.
- GPU, USB, or hardware device passthrough.
- Requiring KVM acceleration.
- A graphical dashboard.
- Production server hosting or Android-wide port exposure by default.
- Transparent access to arbitrary Android application storage.
- Reimplementing Podman behavior in Go.

### 3.3 Product success criteria

- `SUCCESS-001`: A new user on a supported Termux device can install Tusk, run
  Smart Engine qualification, and execute `podman run --rm alpine echo hello`
  without manually installing Linux.
- `SUCCESS-002`: The same device receives a ranked backend report that includes
  every attempted candidate, rejection reasons, benchmark evidence, and the
  selected backend.
- `SUCCESS-003`: A representative Compose project can build, start, expose a
  TCP service, persist a named volume, restart, and tear down.
- `SUCCESS-004`: No acceptance flow uses simulation mode or Tusk-owned
  container lifecycle logic.
- `SUCCESS-005`: A failed operation returns an accurate non-zero status and
  leaves recoverable state.

## 4. Users and Core Journeys

### 4.1 Primary user

Pengguna utama adalah developer atau learner yang hanya memiliki Android dan
Termux, tidak memiliki root, tetapi ingin mencoba image OCI, Dockerfile, dan
Compose dengan command yang familiar.

### 4.2 Required journeys

#### Fresh install and automatic backend selection

```sh
curl -fsSL https://example.invalid/tusk/install.sh | sh
tusk engine tune --mode quick --apply
podman run --rm alpine echo hello
```

The final release URL will replace the placeholder domain. The installer MUST
verify downloaded artifacts before execution or installation.

#### Daily use

```sh
cd ~/.tusk/workspaces/my-app
podman build -t my-app .
podman run --rm -p 8080:8080 my-app
```

#### Compose use

```sh
cd ~/.tusk/workspaces/my-stack
podman compose up -d
podman compose ps
podman compose logs
podman compose down
```

#### Inspect and override Smart Engine selection

```sh
tusk engine list --ranked
tusk engine explain
tusk engine use qemu-system-x86_64
podman run --rm --platform linux/amd64 vendor/legacy-image:latest
```

#### Diagnosis

```sh
tusk status
tusk doctor
tusk logs engine
tusk logs backend
```

## 5. System Architecture

### 5.1 High-level design

```text
Android / Termux host
+-------------------------------------------------------------------+
| podman shim                     tusk CLI                            |
| - argv/stdin/out/tty            - install/update                    |
| - compose passthrough           - Smart Engine                     |
| - real Podman UX                - shares/ports/diagnostics          |
|          |                              |                           |
|          +---------- backend adapter ---+                           |
|                         |                                         |
+-------------------------|-----------------------------------------+
                          |
              +-----------+------------+------------------+
              |                        |                  |
        proot backend         QEMU ARM64 backend   QEMU x86 backend
              |                        |                  |
              +----------- real Podman instance(s) ------+
                                      |
                    OCI runtime / network / storage / build
+-------------------------------------------------------------------+
```

### 5.2 Ownership boundaries

| Concern | Owner |
|---|---|
| Host installation and updates | Tusk |
| Guest image download and verification | Tusk |
| Candidate discovery, conformance, benchmark, scoring | Tusk Smart Engine |
| Backend selection and state locking | Tusk Smart Engine |
| Proot environment lifecycle | Proot backend adapter |
| QEMU configuration and lifecycle | QEMU backend adapters |
| SSH/local transport selection | Backend adapter |
| Host-to-guest path translation | Tusk |
| Host port integration | Backend adapter |
| Image pull and image metadata | Podman |
| Container lifecycle and exec | Podman |
| Dockerfile/Containerfile build | Podman/Buildah |
| Container network semantics | Podman/Netavark |
| Named volumes | Podman |
| Compose semantics | Guest Compose provider |
| Process/emulation mechanics | Proot or QEMU, according to backend |

### 5.3 Architecture requirements

- `ARC-001`: The host implementation MUST be a single versioned `tusk` binary
  plus an optional `podman` shim that resolves to that binary.
- `ARC-002`: Invoking the binary as `podman` MUST activate Podman forwarding mode.
- `ARC-003`: Invoking the binary as `podman-compose` MAY activate legacy Compose
  forwarding mode.
- `ARC-004`: Tusk MUST communicate with Podman through standard interfaces:
  SSH command execution and/or Podman's documented API.
- `ARC-005`: Tusk-specific backend management MUST remain outside Podman's
  command namespace and use `tusk engine ...`.
- `ARC-006`: No backend MUST run a custom Tusk container daemon that replaces
  Podman behavior.
- `ARC-007`: QMP, when used by a QEMU backend, MUST be available only through a
  host-local Unix socket.
- `ARC-008`: Podman's API MUST be exposed to the host through the selected
  backend's authenticated local transport; unauthenticated TCP is prohibited.
- `ARC-009`: Tusk MUST treat Podman as the source of truth and MUST reconcile
  derived host state from Podman after interruption.
- `ARC-010`: Host-side state MUST be limited to Smart Engine evidence, backend
  integration, configuration, locks, forwarding, downloads, and diagnostics.

## 6. Smart Engine and Backend Selection Contract

### 6.1 Purpose

Smart Engine tidak boleh memilih backend berdasarkan nama, asumsi arsitektur,
atau benchmark dari perangkat lain. Ia harus mengumpulkan bukti pada perangkat
aktual. Correctness adalah hard gate; performance baru dibandingkan setelah
Podman terbukti benar-benar bekerja.

### 6.2 Initial candidate catalog

| Candidate ID | Environment | Intended value | Initial status |
|---|---|---|---|
| `proot-native` | Linux rootfs under proot, host architecture | Lowest startup and memory if Podman works correctly | Experimental, must prove feasibility |
| `proot-qemu-user-x86_64` | Proot rootfs with qemu-user translation | Cross-architecture without a full system VM | Experimental, must prove Podman and OCI runtime behavior |
| `qemu-system-aarch64` | Full ARM64 Linux VM | Strong compatibility on ARM64 devices | Required candidate on ARM64 host |
| `qemu-system-x86_64` | Full AMD64 Linux VM | Compatibility with common/legacy AMD64 images | Required candidate where package and storage allow |
| `qemu-system-i386` | Full 32-bit x86 Linux VM | Probe old x86-only compatibility | Experimental; rejection is acceptable |
| `qemu-system-arm` | Full 32-bit ARM Linux VM | Probe ARMv7 devices/images | Experimental where applicable |

The catalog is extensible. Inclusion means "must be attempted when applicable",
not "must be selected". A backend that cannot run real Podman is rejected.

### 6.3 Selection pipeline

```text
discover -> preflight -> bootstrap probe -> Podman conformance
         -> reliability repetitions -> benchmark -> normalize -> rank
         -> explain -> select/apply -> continuously observe
```

1. **Discover:** record host architecture, Android/Termux versions, kernel
   exposure, available binaries, CPU count, RAM, storage, and acceleration.
2. **Preflight:** eliminate impossible candidates without large downloads and
   record an exact reason.
3. **Bootstrap probe:** acquire the smallest signed probe artifact needed to run
   each applicable candidate.
4. **Conformance:** run real Podman health, pull, run, exec, network, volume,
   build, persistence, and cleanup tests.
5. **Reliability:** repeat critical startup/run/stop paths and reject flaky
   candidates above the declared threshold.
6. **Benchmark:** measure startup, command latency, pull/run/build throughput,
   peak and idle memory, CPU use, storage growth, and shutdown.
7. **Rank:** apply a versioned deterministic scoring policy only to qualified
   candidates.
8. **Apply:** initialize the chosen backend and persist the complete decision
   evidence.

### 6.4 Default optimization policy

"Best" means the highest-ranked qualified backend under an explicit policy; it
does not mean the shortest single benchmark. Policy version 1 defines a
provisional `balanced` score from normalized device-local measurements:

| Dimension | Weight | Meaning |
|---|---:|---|
| Reliability | 25% | Repeat success, clean recovery, stable lifecycle |
| Interactive latency | 20% | Start, exec, and CLI round-trip responsiveness |
| Workload throughput | 15% | Pull, unpack, run, and build completion rate |
| Peak and idle memory | 15% | Mobile memory pressure and idle footprint |
| Startup/shutdown | 10% | Cold/warm readiness and clean stop time |
| Persistent storage | 10% | Runtime artifacts and workload data overhead |
| Thermal stability | 5% | Performance retained without sustained throttling |

Mandatory Podman conformance, platform compatibility, security constraints, and
recovery correctness are pass/fail gates outside the weighted score. Smart
Engine MAY provide `speed`, `low-memory`, and `compatibility` policies with
different versioned weights. The report must always include raw values so the
score is auditable.

### 6.5 Smart Engine requirements

- `ENG-001`: Smart Engine MUST discover candidates dynamically from the device
  and packaged candidate catalog.
- `ENG-002`: Smart Engine MUST attempt every applicable candidate in the selected
  tuning mode and MUST report skipped candidates with reasons.
- `ENG-003`: Availability of a binary MUST NOT count as backend qualification.
- `ENG-004`: A candidate MUST pass the mandatory real Podman conformance suite
  before receiving a performance score.
- `ENG-005`: Fake responses, command stubs, or a passing `podman version` alone
  MUST NOT qualify a candidate.
- `ENG-006`: A failed proot candidate MUST be rejected honestly; Smart Engine
  MUST NOT weaken conformance merely to prefer lower overhead.
- `ENG-007`: Benchmark workloads, dataset/image digests, repetitions, warmup,
  timeouts, and scoring policy MUST be versioned.
- `ENG-008`: Rankings MUST be deterministic for the same evidence and policy.
- `ENG-009`: Correctness and reliability are hard gates and MUST outweigh speed.
- `ENG-010`: The default score SHOULD consider startup latency, command latency,
  workload throughput, peak/idle memory, CPU time, disk consumption, and feature
  coverage.
- `ENG-011`: `quick` mode MUST test all applicable candidates with compact probe
  artifacts; `thorough` mode MUST run the full benchmark and repeated reliability
  suite.
- `ENG-012`: Smart Engine MUST print a ranked report with raw measurements,
  normalized scores, rejection reasons, selected backend, and tradeoffs.
- `ENG-013`: Selection evidence MUST be cached against a fingerprint containing
  device, OS, Termux, Tusk, backend binary, probe image, and policy versions.
- `ENG-014`: Cache MUST be invalidated when a fingerprint input changes or when
  the user requests `--force`.
- `ENG-015`: Users MUST be able to override automatic selection explicitly.
- `ENG-016`: Tusk MUST warn when an override selected an unqualified or lower
  ranked backend and MUST require `--allow-unqualified` for failed candidates.
- `ENG-017`: Backend stores MUST be isolated; Smart Engine MUST NOT silently
  switch an existing Podman store to another backend.
- `ENG-018`: Automatic fallback MAY occur only before persistent user resources
  are created, or after an explicit migration/selection decision.
- `ENG-019`: Image architecture and requested `--platform` MUST participate in
  compatibility scoring, but MUST NOT cause invisible per-command store splits.
- `ENG-020`: The selected backend MUST be re-evaluatable without deleting other
  backend instances or their evidence.
- `ENG-021`: Candidate probing MUST have storage, download, runtime, and thermal
  budgets suitable for mobile devices.
- `ENG-022`: Tuning interruption MUST be resumable and MUST leave no backend
  falsely marked qualified.
- `ENG-023`: Smart Engine SHOULD detect sustained thermal throttling and mark
  affected performance results rather than presenting them as clean evidence.
- `ENG-024`: Backend adapters MUST expose a common lifecycle, command, API,
  filesystem, network, health, metrics, and cleanup contract.
- `ENG-025`: If no qualified backend is selected, the first interactive Podman
  command MUST offer or trigger quick tuning before attempting the workload.
- `ENG-026`: Non-interactive Podman use without a qualified backend MUST fail
  with an exact `tusk engine tune --mode quick --apply` recovery command unless
  auto-tuning was explicitly enabled.
- `ENG-027`: `balanced` MUST be the default optimization policy unless the user
  selects another policy.
- `ENG-028`: Smart Engine MUST select the highest score among candidates that
  pass all hard gates for the requested policy and platform.
- `ENG-029`: Score ties MUST use documented deterministic tie-breakers: lower
  peak memory, then lower storage, then stable candidate ID ordering.
- `ENG-030`: Policy name, version, weights, normalized values, final score, and
  tie-break decisions MUST be persisted with selection evidence.

```text

tusk engine list [--ranked]
```

### 6.7 Backend instance behavior

- `PROF-001`: Every initialized backend instance MUST have isolated Podman data,
  logs, process identity, integration sockets, and derived state.
- `PROF-002`: Only one backend instance MAY be selected for normal Podman shim
  commands at a time.
- `PROF-003`: Multiple backend instances MAY remain installed and stopped.
- `PROF-004`: Switching the selected backend MUST require an explicit command
  and MUST explain that Podman resources are backend-local.
- `PROF-005`: `TUSK_ENGINE=<candidate>` MAY override selection for one command,
  but MUST NOT bypass qualification or silently split persistent state.
- `PROF-006`: Backend deletion MUST require explicit confirmation or `--force`
  and identify the Podman resources that will be deleted.

## 7. Runtime Environment Contract

### 7.1 Packaged environment baseline

The initial packaged Linux environment baseline is a pinned Alpine Linux stable
release where feasible. A backend MAY require a different minimal distribution,
but every variation must pass the same Podman conformance contract and declare
its exact stack. Distribution size alone is not a selection criterion.

- `GST-001`: Official releases MUST provide signed probe and runtime artifacts
  for every packaged backend candidate.
- `GST-002`: Runtime environments MUST initialize non-interactively without a
  manual distribution or ISO installation.
- `GST-003`: Candidate environments MUST expose the same conformance interface
  even when implementation details differ.
- `GST-004`: QEMU guests MUST provide required kernel facilities; proot
  candidates MUST prove equivalent observable Podman behavior rather than claim
  unavailable kernel capabilities.
- `GST-005`: Each runtime environment MUST include pinned compatible versions of
  Podman, an OCI runtime, networking helpers, storage helpers, one Compose
  provider, and the adapter-specific transport tools; QEMU includes SSH while
  proot does not require an SSH server.
- `GST-006`: QEMU backends SHOULD use rootful Podman. Proot candidates MAY use a
  different mode only if the mode passes the same required workflows.
- `GST-007`: Podman storage MUST reside in backend-local persistent storage, not
  in a disposable probe or root filesystem.
- `GST-008`: Each backend MUST make Podman command execution and API readiness
  available through its adapter contract.
- `GST-009`: Podman API socket paths MUST be versioned in backend metadata.
- `GST-010`: Podman API MUST NOT listen on an unauthenticated external TCP
  interface.
- `GST-011`: The environment MUST provide a health command that verifies cgroups,
  storage, networking, DNS, Podman, and Compose provider availability.
- `GST-012`: Probe and runtime artifact build inputs MUST be reproducible and
  version-controlled.
- `GST-013`: Release metadata MUST state environment distribution, kernel or
  host-kernel exposure, Podman, Compose provider, OCI runtime, networking, and
  storage versions.
- `GST-014`: The runtime environment MUST use UTC internally; user-visible
  timestamps MAY be rendered using the host timezone.
- `GST-015`: Backend-local persistent storage MUST be mounted or activated before
  Podman is considered ready.

### 7.2 Persistence model

QEMU and proot have different storage mechanics but the same durability contract:

| Artifact | Purpose | Update behavior |
|---|---|---|
| QEMU `system.qcow2` | Bootable guest OS and packaged tools | Replaceable through verified update |
| QEMU `data.qcow2` | Podman storage and durable guest state | Preserved across system updates |
| Proot `rootfs/` | Linux userspace and packaged tools | Replaceable through verified update |
| Proot `data/` | Podman storage and durable runtime state | Preserved across rootfs updates |

- `DAT-001`: Runtime environment replacement MUST NOT delete backend-local Podman
  data.
- `DAT-002`: Persistent storage MUST be checked or recovered after an unclean
  exit before Podman is marked ready.
- `DAT-003`: Data format changes MUST include a versioned migration and rollback
  or a release-blocking incompatibility warning before modification.
- `DAT-004`: Tusk MUST report required and available storage before download,
  extraction, disk growth, and backup operations.
- `DAT-005`: Sparse qcow2 files and filesystem-efficient proot storage SHOULD be
  used where supported.
- `DAT-006`: Automatic persistent storage growth MAY be supported; automatic
  shrinking MUST NOT be attempted.

## 8. Host State and Filesystem Layout

### 8.1 Canonical layout

```text
~/.tusk/
|-- config.json
|-- release.json
|-- locks/
|   `-- global.lock
|-- downloads/
|-- workspaces/
|-- run/
|   `-- <backend-id>/
|       |-- podman.sock
|       |-- qmp.sock
|       `-- ssh-control.sock
|-- engines/
|   `-- <backend-id>/
|       |-- system/ or rootfs/
|       |-- data/
|       |-- state.json
|       |-- process.json
|       |-- evidence.json
|       `-- logs/
|-- benchmarks/
|   `-- <device-fingerprint>/
|-- keys/
|   |-- guest_ed25519
|   `-- guest_ed25519.pub
`-- shares.json
```

- `STATE-001`: Runtime sockets MUST be created with user-only permissions.
- `STATE-002`: Private keys MUST be created with mode `0600` or stricter.
- `STATE-003`: State writes MUST use atomic replace semantics and fsync where
  loss would make recovery ambiguous.
- `STATE-004`: Process state MUST include PID, process start identity, backend,
  executable, and creation timestamp; PID alone is insufficient.
- `STATE-005`: Stale sockets and stale PID files MUST be detected and safely
  removed only after process identity verification.
- `STATE-006`: Tusk MUST use a global lifecycle lock to prevent concurrent
  backend tuning, start, stop, switch, update, or removal races.
- `STATE-007`: Read-only commands SHOULD avoid acquiring an exclusive lock.
- `STATE-008`: Host configuration MUST be schema-versioned.
- `STATE-009`: Unknown newer configuration schemas MUST fail without rewriting
  the file.
- `STATE-010`: Secrets MUST NOT be placed in QEMU command-line arguments, logs,
  or world-readable files.

## 9. Backend Lifecycle Contract

### 9.1 State machine

```text
uninitialized -> downloading -> stopped -> starting -> provisioning -> ready
                                      ^         |             |          |
                                      |         v             v          v
                                      +------ error <------ degraded <- stopping
                                                               |          |
                                                               +-> ready  +-> stopped
```

| State | Meaning |
|---|---|
| `uninitialized` | Required backend artifacts do not exist |
| `downloading` | Verified artifacts are being acquired |
| `stopped` | Complete backend exists and no matching backend process is alive |
| `starting` | Backend process is alive but execution transport is not ready |
| `provisioning` | Backend is reachable; Podman services or migration are not ready |
| `ready` | Persistent storage, Podman, Compose, API bridge, and adapter are healthy |
| `degraded` | VM is usable but one required integration is unhealthy |
| `stopping` | Graceful shutdown is in progress |
| `error` | Recovery or user action is required |

### 9.2 Lifecycle requirements

- `VM-001`: `tusk engine start` MUST be idempotent for every backend adapter.
- `VM-002`: Podman shim commands SHOULD auto-start an initialized stopped
  backend unless `TUSK_NO_AUTO_START=1` is set.
- `VM-003`: Auto-start MUST wait for the `ready` state, not merely socket or
  process existence.
- `VM-004`: Start MUST have phase-specific bounded timeouts and report the last
  successful phase.
- `VM-005`: Start MUST fail when activating the backend would silently conflict
  with another selected backend or its integration endpoints.
- `VM-006`: Every adapter MUST bind control endpoints to loopback or local Unix
  sockets only.
- `VM-007`: QEMU adapters MUST use TCG when acceleration is unavailable; proot
  adapters MUST declare all host kernel assumptions.
- `VM-008`: QEMU TCG multi-threading SHOULD be enabled where supported.
- `VM-009`: CPU and memory defaults MUST be configurable per backend and
  validated against host capacity and benchmark budgets.
- `VM-010`: Graceful stop MUST use the adapter's safest shutdown sequence and
  use KILL only after bounded escalation or `--force`.
- `VM-011`: Stop MUST wait for backend exit and clean runtime sockets.
- `VM-012`: An Android-killed backend process MUST be detected as an unclean exit
  on the next command.
- `VM-013`: Unclean-exit recovery MUST verify the data disk before returning
  `ready`.
- `VM-014`: QEMU adapters MUST provide a serial console; proot adapters MUST
  provide an equivalent diagnostic shell.
- `VM-015`: A backend launch failure MUST include the adapter, executable, log
  path, and categorized cause without leaking secrets.
- `VM-016`: The active backend MUST be discoverable from process identity and
  runtime state even if `state.json` is stale.
- `VM-017`: QEMU machine types and proot/QEMU-user options MUST be pinned per
  Tusk release and covered by upgrade tests.

### 9.3 Readiness checks

Readiness MUST verify all of the following in order:

1. Matching backend process and identity are valid.
2. Adapter control channel succeeds; QMP is additionally required for QEMU.
3. Backend transport identity matches initialized state.
4. Backend authentication, when applicable, succeeds.
5. Persistent data storage is active read-write.
6. `podman info` succeeds.
7. Podman storage and network backends are healthy.
8. Compose provider responds.
9. Podman API socket responds through the backend's local bridge.
10. Host port reconciliation has completed.

## 10. Transport and Command Execution

### 10.1 Transport roles

| Transport | Role |
|---|---|
| Local adapter process | Proot command execution and lifecycle |
| QMP Unix socket | QEMU-only status, graceful control, runtime port forwarding |
| Serial console | QEMU-only boot diagnostics and emergency guest access |
| SSH over loopback host-forward | QEMU authenticated command execution and provisioning |
| Local Unix socket bridge | Podman API access for every selected backend |

### 10.2 SSH requirements

- `TRN-001`: QEMU guest SSH MUST use key authentication generated during backend
  initialization; proot MUST use a direct local adapter without a network login.
- `TRN-002`: Password authentication MUST be disabled in release guest images.
- `TRN-003`: Tusk MUST verify and pin each QEMU backend's SSH host key.
- `TRN-004`: Host key mismatch MUST be a hard failure with an explicit recovery
  command; Tusk MUST NOT silently accept a changed key.
- `TRN-005`: QEMU SSH traffic MUST pass through a loopback-only host forward.
- `TRN-006`: The allocated host SSH port MUST be collision-checked and persisted
  as derived state.
- `TRN-007`: Forwarded execution MUST preserve argv boundaries and MUST NOT
  concatenate untrusted arguments into an injectable shell command.
- `TRN-008`: Non-TTY execution MUST preserve stdin, stdout, and stderr as
  separate streams.
- `TRN-009`: TTY execution MUST allocate a guest PTY, copy terminal size, relay
  resize events, and restore the host terminal on every exit path.
- `TRN-010`: Interrupt, termination, and hangup behavior MUST be defined and
  tested; Ctrl-C MUST target the remote foreground command rather than corrupt
  host state.
- `TRN-011`: Lost transport MUST produce a distinct error from the remote
  command's exit status.
- `TRN-012`: Tusk MUST bound connection and keepalive behavior so Android sleep
  or network suspension cannot hang a command forever without diagnostics.

### 10.3 Podman API bridge

- `API-001`: A ready backend MUST expose a host Unix socket at
  `~/.tusk/run/<backend-id>/podman.sock`.
- `API-002`: QEMU adapters MUST forward the guest Podman socket securely; proot
  adapters MUST bridge or expose their local Podman socket with equivalent access
  control.
- `API-003`: Tusk MUST set or print the correct `DOCKER_HOST` value through
  `tusk env`.
- `API-004`: Podman remote clients MAY use the socket when covered by tests.
- `API-005`: Optional Docker API compatibility MAY use Podman's compatibility
  layer but is secondary and MUST be documented separately.
- `API-006`: API tunnel failure MUST transition a running machine to `degraded`;
  successful repair MAY return it to `ready`.
- `API-007`: Tusk MUST be able to recreate the API bridge without deleting or
  reinitializing the backend.

## 11. Podman CLI Contract

### 11.1 Command model

The installed `podman` command is a thin Tusk forwarding mode, not a replacement
container engine and not a fork of Podman. Tusk forwards the command to real
Podman in the selected backend while adapting working directory, shared paths,
backend selection, ports, and transport.

- `CLI-001`: `podman <args...>` MUST preserve argument ordering and values after
  documented host-path translation.
- `CLI-002`: Unknown Podman options MUST be passed through; Tusk MUST NOT
  silently discard them.
- `CLI-003`: Tusk-owned Podman shim options MUST be namespaced or environment
  based so they cannot collide with Podman options.
- `CLI-004`: `tusk podman <args...>` MUST provide an explicit escape hatch when
  installing a command named `podman` is undesirable.
- `CLI-005`: `podman compose <args...>` MUST invoke the selected backend's pinned Compose
  provider through `podman compose` or an equivalent declared entry point.
- `CLI-006`: The shim MUST preserve remote exit code `0..255` when transport
  succeeds.
- `CLI-007`: Transport and Tusk integration failures MUST use documented Tusk
  exit codes that do not masquerade as remote success.
- `CLI-008`: Human-readable errors MUST go to stderr.
- `CLI-009`: Machine-readable output from Podman MUST pass through unchanged
  unless the user explicitly requests a Tusk output format.
- `CLI-010`: Interactive commands such as `run -it`, `exec -it`, `attach`, and
  `login` MUST be covered by PTY acceptance tests before being marked supported.
- `CLI-011`: Commands run from an unshared working directory MUST fail before
  remote execution when the command depends on local paths.
- `CLI-012`: Podman shim help MUST identify Tusk, the selected backend, and the
  real remote Podman engine.
- `CLI-013`: `podman version` MUST clearly display host shim, Tusk, Smart Engine
  selection, backend environment, and real Podman versions.
- `CLI-014`: `podman info` MUST preserve Podman output and SHOULD prepend no text
  when a machine-readable format is requested.

### 11.2 MVP compatibility matrix

| Workflow | MVP status | Acceptance expectation |
|---|---|---|
| `podman pull` | Required | Real registry pull through selected Podman |
| `podman images` | Required | Lists selected-backend Podman images |
| `podman build` | Required | Builds from a shared context |
| `podman run` foreground | Required | Streams output and exit code |
| `podman run -it` | Required | Working PTY and signal relay |
| `podman run -d` | Required | Persistent backend-local container |
| `podman ps` / `ps -a` | Required | Real Podman is source of truth |
| `podman exec` | Required | Foreground and interactive execution |
| `podman logs` | Required | Podman logs, including `-f` |
| `podman stop/start/restart` | Required | Native Podman semantics |
| `podman rm/rmi` | Required | Native Podman semantics |
| `podman inspect` | Required | Pass-through structured output |
| `podman network` | Required | Native Podman network operations |
| `podman volume` | Required | Native Podman volume operations |
| `podman pod` | Required | Native Podman pod operations |
| `podman save/load` | Required | Streams must not be corrupted |

Compatibility is behavioral and test-based. The host shim must expose real

## 12. Shared Filesystem and Path Translation

### 12.1 Security model

Podman in any selected backend can modify host directories exported read-write.
Tusk therefore does not expose the complete Termux home by default.

The default shared root is:

```text
Host:  ~/.tusk/workspaces
Guest: /mnt/tusk/workspaces
```

### 12.2 Share commands

```text
tusk share list
tusk share add <host-path> [--name <name>] [--read-only]
tusk share remove <name>
```

- `FS-001`: Tusk MUST create and register the default workspace during install.
- `FS-002`: Additional shared roots MUST be explicit and persisted by canonical
  host path.
- `FS-003`: Tusk MUST reject duplicate, overlapping, unsafe, missing, or
  symlink-escaping share definitions unless a documented safe case applies.
- `FS-004`: Adding or removing a backend filesystem export MUST use adapter-safe
  lifecycle rules and require restart when hot updates are unsafe.
- `FS-005`: Every share MUST have a stable, validated guest mount path.
- `FS-006`: Host paths in Podman bind mounts, build contexts, Compose files, and
  working directories MUST be translated to their guest shared-root path.
- `FS-007`: Paths outside registered shared roots MUST fail with the exact host
  path and an actionable `tusk share add` suggestion.
- `FS-008`: Relative paths MUST resolve against the host working directory
  before translation.
- `FS-009`: The remote command's working directory MUST correspond to the host
  working directory when it is under a shared root.
- `FS-010`: Tusk MUST preserve read-only intent for read-only shares and `:ro`
  bind mounts.
- `FS-011`: Tusk MUST not rewrite paths that are explicitly guest-only paths.
- `FS-012`: Path translation MUST support spaces, quotes, Unicode filenames,
  and leading dashes without shell injection.
- `FS-013`: Build contexts MUST be readable from the guest without copying into
  Podman-owned storage first; an optimized sync mode MAY be added later.
- `FS-014`: Tusk MUST document 9p/shared-filesystem performance and file feature
  limitations, including ownership, special files, and filesystem events.
- `FS-015`: Removing a share MUST NOT delete host files.

## 13. Networking and Published Ports

### 13.1 Two-layer networking

A published container port crosses backend-specific boundaries. For QEMU:

```text
Termux host port
    -> QEMU user-network host forward
        -> guest Podman published port
            -> container port
```

Podman owns container publish semantics. Each backend adapter owns any additional
host integration required to make that port reachable from Termux.

### 13.2 Requirements

- `NET-001`: Every backend MUST use networking that requires no Android root.
  QEMU user-mode networking is the initial QEMU baseline.
- `NET-002`: Backend outbound DNS and TCP connectivity MUST pass conformance.
- `NET-003`: TCP ports published by Podman MUST be reconciled through the selected
  backend adapter before Tusk reports the operation fully successful.
- `NET-004`: Host forwards MUST bind `127.0.0.1` by default.
- `NET-005`: Binding `0.0.0.0` or another non-loopback address MUST require an
  explicit opt-in and security warning.
- `NET-006`: Host port availability MUST be checked before creating a forward.
- `NET-007`: A forwarding collision MUST identify the backend, protocol, address,
  port, and conflicting listener when available.
- `NET-008`: Forward creation and removal MUST be idempotent.
- `NET-009`: Tusk MUST rebuild derived forwards from running Podman containers
  after backend restart or unclean host exit.
- `NET-010`: Removing or stopping the owning container/Compose project SHOULD
  remove its no-longer-needed host forward.
- `NET-011`: QMP/monitor forwarding for QEMU and local forwarding for proot MUST
  be capability-checked against the selected adapter version.
- `NET-012`: A failed host-forward reconciliation MUST be visible as degraded
  state and MUST NOT be reported as a fully working published service.
- `NET-013`: MVP MUST support TCP publish syntax `hostPort:containerPort` and
  `hostIP:hostPort:containerPort` for valid host addresses.
- `NET-014`: UDP publishing is deferred until it passes real-device tests; use
  before that point MUST fail honestly rather than creating only half a route.
- `NET-015`: Automatic random host ports MUST be discoverable through a Tusk
  command or native Podman port output.
- `NET-016`: Port state is derived integration state; Podman remains the source
  of truth for container publish configuration.

## 14. Compose Contract

### 14.1 Model

Tusk does not parse Compose to orchestrate containers. The selected backend's
pinned Compose provider owns Compose semantics. Tusk only ensures that the
project is accessible, forwards the invocation, and reconciles host ports.

- `CMP-001`: `podman compose` MUST execute through the selected backend.
- `CMP-002`: The Compose provider and version MUST be declared in backend
  metadata and `podman version` diagnostics.
- `CMP-003`: The guest working directory MUST map to the host project directory.
- `CMP-004`: Compose file arguments, `.env`, `env_file`, build contexts, and bind
  mount paths MUST resolve under registered shared roots.
- `CMP-005`: MVP MUST cover `config`, `build`, `pull`, `up`, `down`, `ps`, `logs`,
  `exec`, `run`, `stop`, `start`, `restart`, and `rm` for the tested subset.
- `CMP-006`: `up -d` MUST return only after Podman resources exist and required
  host TCP forwarding has reconciled.
- `CMP-007`: `down` MUST affect only resources selected by the Compose provider's
  project identity; Tusk MUST NOT globally delete containers.
- `CMP-008`: Named volume persistence MUST be owned by Podman and survive
  `down` unless the provider is explicitly asked to remove volumes.
- `CMP-009`: Unsupported Compose fields MUST surface provider warnings or errors;
  Tusk MUST NOT suppress them.
- `CMP-010`: Tusk MUST publish a tested Compose feature matrix rather than claim
  complete Compose Specification compliance.
- `CMP-011`: Compose command exit code and output streams MUST pass through.
- `CMP-012`: A port reconciliation failure after resource creation MUST report
  that guest resources may be running and provide an exact cleanup command.

## 15. Installation, Provisioning, and Distribution

### 15.1 Installation requirements

- `INS-001`: The installer MUST verify it is running in a supported Termux
  environment before changing files.
- `INS-002`: The installer MUST install or verify required host packages through
  Termux package tooling.
- `INS-003`: Required packages MUST be architecture and candidate aware. Initial
  installation SHOULD install lightweight discovery dependencies first and let
  Smart Engine request larger backend packages only when applicable.
- `INS-004`: The host binary and guest image metadata MUST be downloaded over
  HTTPS and verified against a signed release manifest.
- `INS-005`: The release manifest MUST be signed by an embedded, rotatable
  project key and include SHA-256 digests and exact byte sizes.
- `INS-006`: A checksum, signature, content type, or size mismatch MUST delete or
  quarantine the artifact and fail installation.
- `INS-007`: Downloads SHOULD be resumable and MUST use temporary partial names
  until verification succeeds.
- `INS-008`: Installation MUST be idempotent and safe to rerun.
- `INS-009`: Installation MUST NOT require cloning the source repository or
  installing a Go toolchain.
- `INS-010`: Guest initialization MUST be non-interactive unless credentials or
  destructive choices require explicit consent.
- `INS-011`: The installer MUST NOT report runtime success before at least one
  backend passes real Podman qualification and a smoke test.
- `INS-012`: Installing the `podman` shim MUST detect command collisions and
  require an explicit choice instead of overwriting an unrelated binary.
- `INS-013`: Shell profile modification MUST be minimal, idempotent, displayed,
  and reversible.
- `INS-014`: Installation logs MUST be stored under `~/.tusk` with secrets
  redacted.
- `INS-015`: Minimum free-space checks MUST account for compressed downloads,
  extracted system images, data disks, and temporary verification space.

### 15.2 Runtime environment provisioning

- `PRV-001`: QEMU first boot MUST inject only the generated SSH public key and
  versioned non-secret configuration; proot provisioning MUST not create an
  unnecessary network authentication surface.
- `PRV-002`: Provisioning MUST be restartable after interruption.
- `PRV-003`: Provisioning steps MUST be idempotent and individually logged.
- `PRV-004`: A backend MUST not become `ready` when packaged environment versions differ
  from release metadata beyond an explicitly supported range.
- `PRV-005`: Provisioning MUST run the guest conformance health command.
- `PRV-006`: Tusk SHOULD minimize writes to the replaceable system disk.

## 16. Update, Backup, and Uninstall

### 16.1 Update

- `UPD-001`: `tusk update check` MUST report host binary, system image, guest
  stack, schema, and data migration changes separately.
- `UPD-002`: Updates MUST verify signed metadata and artifacts using the same
  trust rules as installation.
- `UPD-003`: Runtime environment updates MUST require the affected backend to be stopped.
- `UPD-004`: Tusk MUST preserve the previous host binary and runtime environment until
  the updated backend passes readiness and smoke checks.
- `UPD-005`: Failed health checks MUST trigger or offer rollback without deleting
  the persistent data disk.
- `UPD-006`: A required irreversible data migration MUST require an explicit
  backup and user confirmation.
- `UPD-007`: Tusk MUST NOT update Podman independently to an unqualified version.

### 16.2 Backup and restore

- `BKP-001`: `tusk backup <backend>` MUST require a stopped or consistently
  quiesced backend.
- `BKP-002`: Backup metadata MUST include backend ID and architecture, Tusk
  version, runtime environment version, data schema, checksum, and creation time.
- `BKP-003`: Restore MUST validate architecture, checksum, capacity, and schema
  compatibility before replacing state.
- `BKP-004`: Restore MUST be transactional and preserve the previous backend state
  until validation succeeds.
- `BKP-005`: Shared host workspace content is outside backend backup scope and
  MUST be documented as such.

### 16.3 Uninstall

- `UN-001`: Uninstall MUST stop the active machine safely before removing Tusk
  runtime files.
- `UN-002`: Uninstall MUST distinguish binaries/configuration from backend data.
- `UN-003`: Deleting backend Podman data MUST require explicit consent.
- `UN-004`: Uninstall MUST NOT delete registered host shares or user workspaces.
- `UN-005`: Uninstall MUST remove only shell modifications that Tusk can identify
  as its own.
- `UN-006`: A non-interactive destructive uninstall MUST require an explicit
  `--purge-data` style flag.

## 17. Security and Trust Model

### 17.1 Trust boundaries

Backend boundaries have different isolation strengths. A QEMU guest provides a
kernel boundary; proot does not provide equivalent isolation. Podman and exported
host directories still grant substantial power. Smart Engine MUST expose this
security difference in scoring and explanations.

- `SEC-001`: Tusk MUST use least exposure: local Unix sockets, loopback SSH, and
  explicit shared roots.
- `SEC-002`: Podman API MUST never be exposed through unauthenticated TCP.
- `SEC-003`: QMP MUST never listen on a non-local network address.
- `SEC-004`: Release artifacts MUST be authenticated, not merely checksummed
  against an unsigned file from the same server.
- `SEC-005`: Remote command arguments, environment, working directory, and paths
  MUST be resistant to shell injection.
- `SEC-006`: Logs MUST redact registry passwords, auth tokens, private keys, and
  environment values marked secret.
- `SEC-007`: Private keys MUST not leave the Termux application sandbox unless
  the user explicitly exports them.
- `SEC-008`: Shared-root registration MUST show whether access is read-only or
  read-write and explain the guest-root risk.
- `SEC-009`: The default workspace MUST not include `~/.ssh`, Termux auth files,
  Android app data, or the whole Termux home.
- `SEC-010`: Tusk MUST validate archive extraction paths and reject traversal,
  absolute-path, device-node, and unsafe link entries in downloaded artifacts.
- `SEC-011`: Tusk MUST use secure temporary file creation and avoid predictable
  secret paths.
- `SEC-012`: Update key rotation MUST require a manifest signed by a currently
  trusted key and include rollback protections.
- `SEC-013`: Tusk MUST not send telemetry by default.
- `SEC-014`: A security report process and supported-version policy MUST exist
  before a public stable release.
- `SEC-015`: Registry credentials MUST remain inside the selected backend
  unless an explicit import/export feature is used.

## 18. Error and Recovery Contract

### 18.1 Error categories

| Category | Example | Required actionability |
|---|---|---|
| Configuration | Invalid backend or resource value | Show field and valid values |
| Dependency | Missing proot/QEMU binary | Show exact Termux package/action |
| Download | Interrupted or corrupt image | Show resume/retry and artifact path |
| Backend boot | Proot/QEMU exits or readiness timeout | Show adapter, phase, log, recovery command |
| Authentication | SSH host key mismatch | Show safe reset/reprovision command |
| Guest health | Podman or storage unavailable | Show guest health detail and logs |
| Path | Directory outside shared roots | Show `tusk share add` command |
| Port | Host port collision | Show address, port, protocol, owner if known |
| Compatibility | Unsupported Podman/backend behavior | State adapter or provider limitation |
| State | Stale PID/socket or interrupted update | Show automatic and manual recovery |

- `ERR-001`: Every failure MUST identify whether it originated in Tusk, Smart
  Engine, proot, QEMU, transport, runtime environment, Podman, Compose provider,
  or the container command.
- `ERR-002`: Errors MUST preserve causal context without dumping secrets.
- `ERR-003`: Retriable and destructive recovery actions MUST be distinguished.
- `ERR-004`: Tusk MUST not automatically delete persistent disks to recover.
- `ERR-005`: Timeout errors MUST state the timed operation and elapsed limit.
- `ERR-006`: Partial success MUST state what exists and provide inspection and
  cleanup commands.
- `ERR-007`: Machine-readable error output MAY be added, but its schema MUST be
  versioned before stability is promised.
- `ERR-008`: A panic or stack trace MUST not be the default user experience.

### 18.2 Tusk-owned exit codes

Remote Podman/container exit codes take precedence after successful transport.
When no remote command starts, Tusk uses:

| Code | Meaning |
|---|---|
| `64` | Invalid Tusk usage or configuration |
| `69` | Required service/backend unavailable |
| `70` | Internal Tusk integration failure |
| `74` | Host or guest I/O failure |
| `75` | Temporary failure; retry may succeed |
| `77` | Authentication or permission failure |
| `78` | Unsupported or invalid environment |

The implementation MUST document collision handling for remote commands that
legitimately return the same values; stderr origin text remains authoritative.

## 20. Performance and Resource Policy

Correctness is more important than speed, but unbounded resource use is not
acceptable on mobile.

- `PERF-001`: Default vCPU and RAM values MUST be conservative and configurable.
- `PERF-002`: Start MUST warn before allocating settings likely to exhaust the
  detected device memory.
- `PERF-003`: Resource defaults SHOULD be derived from backend evidence and host
  constraints rather than fixed architecture labels.
- `PERF-004`: Every candidate report MUST identify emulation/translation layers
  and warn when measured overhead is substantial.
- `PERF-005`: Idle guest services SHOULD minimize CPU wakeups.
- `PERF-006`: Downloads and disk operations SHOULD expose progress without
  producing excessive terminal output.
- `PERF-007`: Release qualification MUST record, but need not universally gate,
  cold boot, warm boot, pull, build, run, Compose, and shutdown timing on named
  reference devices.
- `PERF-008`: Performance optimizations MUST NOT bypass verification, isolation,
  or durable state rules.

```json
  "autoStart": true,
  "smartEngine": {
```

  which overrides built-in defaults, unless a command documents otherwise.
- `CFG-003`: Environment variables owned by Tusk MUST use the `TUSK_` prefix.
- `CFG-004`: Unknown keys SHOULD be preserved by safe config updates when schema
  compatibility permits.
- `CFG-005`: Invalid configuration MUST fail before starting, tuning, or mutating
  a backend.
- `CFG-006`: `tusk config show --effective` MUST display effective non-secret
  configuration and its sources.

## 22. Engineering Quality Contract

- `QLT-007`: Release builds MUST be reproducible enough to compare declared

- `QLT-008`: Dependencies MUST be pinned and reviewed for license and security.

### 23.3 Real-device release gate

A release MUST NOT be called MVP-complete until `AT-001` through `AT-036` pass
on at least:

1. One supported ARM64 Android device with a fresh Termux installation.
2. One constrained reference device near minimum RAM/storage support.
3. Proot and every packaged QEMU architecture candidate applicable to the device.
4. At least one test run without KVM or other hardware acceleration.

Device model, Android version, Termux version, package repository, available
RAM, available storage, and timing results MUST be recorded.

## 25. Definition of Done

A requirement is done only when:

1. Its behavior is implemented without placeholders.
2. Unit or contract tests cover deterministic logic.
3. Relevant backend/Podman integration tests pass.
4. User-visible behavior and failure semantics are documented.
5. Security-sensitive behavior has negative tests.
6. The requirement ID appears in implementation and test traceability records.
7. Real-device evidence exists when the behavior depends on Termux or Android.

The MVP is done only when:

- Smart Engine attempts every applicable packaged candidate.
- At least one backend is qualified and selected from real evidence.
- The mandatory Podman compatibility subset passes.
- Compose, shared storage, and TCP publishing pass end-to-end.
- Install, update rollback, backup/restore, and uninstall are recoverable.
- No fake implementation or simulation path exists.
- Known incompatibilities are published and produce honest failures.

## 26. Decision Log

| Decision | Status | Rationale |
|---|---|---|
| Podman is the real and primary CLI/engine | Accepted | Avoid fake Docker/runtime behavior |
| Smart Engine selects from measured evidence | Accepted | No backend is universally optimal |
| Proot must be tried, not assumed viable | Accepted | Prefer low overhead only after conformance |
| QEMU ARM64/x86_64 and applicable 32-bit variants are candidates | Accepted | Explore compatibility/performance tradeoffs empirically |
| Correctness and reliability gate performance scoring | Accepted | Fast but broken is not useful |
| Backend stores remain isolated | Accepted | Prevent invisible state splits and corruption |
| One backend selected for normal commands | Accepted for MVP | Keep Podman state and UX understandable |
| QEMU TCG requires qualification without KVM | Accepted | Android generally hides hardware acceleration |
| Transport is adapter-specific | Accepted | Local proot and SSH/QMP QEMU need different mechanics |
| Podman API uses a protected local bridge | Accepted | Support remote tooling without unsafe TCP exposure |
| Explicit shared roots | Accepted | Avoid exposing the entire Termux home to guest root |
| QEMU user networking is the initial QEMU baseline | Accepted for MVP | Works without root or TAP/TUN |
| TCP publish required, UDP deferred | Accepted for MVP | Deliver a complete tested path before broad claims |
| Alpine is a provisional environment baseline | Accepted provisionally | Size is useful, conformance is mandatory |
| Prebuilt signed probe/runtime artifacts | Accepted | Repeatable non-interactive candidate testing |

Future changes to accepted architecture decisions require an ADR that references
this spec and updates affected requirement and acceptance IDs.

## 28. Open Validation Items

These are engineering validations, not permission to weaken product goals:

1. Prove or reject real Podman feasibility under `proot-native` using the full
   conformance suite, including cgroups, OCI runtime, networking, and persistence.
2. Prove or reject `proot-qemu-user-x86_64` without weakening correctness gates.
3. Qualify exact Linux environments and Podman stacks for QEMU ARM64, x86_64,
   i386, and ARM32 candidates where packages are available.
4. Benchmark QEMU ARM `virt` and x86 machine/device choices on reference phones.
5. Confirm dynamic QEMU user-network forwarding behavior through pinned QMP and
   monitor interfaces.
6. Validate shared-filesystem behavior for Podman bind mounts, build contexts,
   ownership, file watching, and read-only exports under every qualified backend.
7. Validate SSH Unix-socket forwarding in Termux OpenSSH and the equivalent local
   Podman socket bridge for proot.
8. Establish scoring weights, reliability thresholds, thermal policy, quick-mode
   budgets, minimum RAM, and minimum free storage from measured devices.
9. Select permanent release hosting, signing custody, and key rotation process.
10. Select and add the repository's final open-source license.

If an item fails validation, the resulting design change MUST preserve the
ownership boundary: Podman remains the container engine, Smart Engine remains
the evidence-based selector, backend adapters provide execution boundaries, and
Tusk remains the integration layer.
